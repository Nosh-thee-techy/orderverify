# Three-minute demo

Use "Try with sample orders". Leave the statement off for the first run. Turn it on for the second.

## 0:00 Problem (15s)

Akinyi sells clothes on WhatsApp. Buyers send a screenshot that says the money was paid. Some of those messages were edited. She has already lost stock.

## 0:15 A forged order is held (45s)

Open the sample. Run it as messages only. Show the order whose code says one date and the message says another. Read the plain sentence. It is on hold. Show the spouse payment as "check first", not as an accusation. Point at the outline badge on a clean order: it looks consistent, and it says it was not checked against M-Pesa records.

## 1:00 The payment (45s)

Run again with the statement included, or start a fresh sample and include it. On the activity screen, show Payment required, then Paid, then Report delivered. Open the transaction in the explorer if this run used live mode. If the red BYPASS banner is up, say so: that run was not a real payment. The fabricated-code order that looked fine as text is now held, because the receipt is not on the statement. The edited amount (message 2,500, statement 250) is held for the same reason.

## 1:45 The cap (30s)

Open Wallet. Set the weekly cap to 0. Run another check. The server refuses. The banner says the weekly budget is used up. Raising the cap is the only way through. The browser cannot skip this.

## 2:15 Limits and the numbers (30s)

Open the limits panel, then /evals. Text-only misses the made-up codes. The statement catches them. The false-flag rate is on the page, including any nickname that did not share a name token. Do not apologise for the miss. It is the reason the statement exists.

## 2:45 Close (15s)

About KES 1.3 per check. No subscription. She sets the cap. The same paid check can be called by another tool later.
